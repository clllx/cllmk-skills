## 第 1 步：前置鉴权

执行前须已通过 `<skill-dir>/SKILL.md` 的「业务公共前置」，确认当前会话 **`data.system === "people"`**。会话是 ATS 时停止，按 `SKILL.md` 业务公共前置第 5 条执行 `cllmk people pp auth login`，用户只在弹出的 Chrome 里完成认证。

## 第 2 步：判断 Tab 与操作类型

**先定 Tab，再定操作。** 两个 Tab 的可用字段类型与 payload 键集合都不同，选错会构造出错误的请求。

| 用户表达 | Tab | moduleId |
|---|---|---|
| 部门字段 / 部门信息 / 部门基础信息 / 部门属性 / 部门编号 / 部门类型 / 上级部门 | **部门信息** | `6` |
| 组织职责 / 部门职责 / 职责 / 分管负责人 / 部门负责人 / HRBP / 财务BP / 「部门上关联人员」 | **组织职责** | `7` |
| 只说「部门字段」但描述的是「谁负责这个部门」 | **停下询问**：是加一个部门属性，还是加一个组织职责？ |

| 触发关键词 | 操作 | 去向 |
|---|---|---|
| 查看 / 查询 / 列出 / 有哪些 / 导出 | **查询** | §5.1 |
| 创建 / 新增 / 新建 / 添加 / 加一个 | **创建** | 第 3 步 → §5.3 |
| 修改 / 更新 / 改名 / 改为 / 变更 | **编辑** | 第 3 步 → §5.4 |
| 停用 / 禁用 / 关闭 / 下线 | **停用** | 第 3 步 → §5.5 |
| 启用 / 开启 / 恢复 / 重新启用 | **启用** | 第 3 步 → §5.5 |
| 删除 / 移除 | 不在本 skill 覆盖范围，见「不覆盖清单」，建议改用停用 | — |

## 第 3 步：定位目标（Tab → 字段）

数据是两层结构：**Tab（moduleId）→ 字段（attrId）**。

本页**没有分组管理**：两个 Tab 各自只有一个系统内置分组（`status == 0`），用户不能新建、改名或停用分组。分组在这里只是取 `modelId` 的载体，不是需要用户选择的层级。

### 3.1 确定 Tab → moduleId

按第 2 步的表得到 `moduleId`（`6` 或 `7`）。**用户没说清是哪个 Tab 时不要猜**，按字段语义给建议并确认：值是「一段文字 / 一个日期 / 一个是非 / 一个选项」→ 部门信息；值是「某个人」→ 组织职责。

### 3.2 读取该 Tab 的分组与字段

```bash
cllmk curl \
  --url "/api/organization/v1/model/list?bus=20" \
  --method POST \
  --payload '{"loginType":"10","moduleId":<6|7>}'
```

响应内层 `data` 是分组数组，**恒为 1 个元素**。该元素含 `id`（= 写接口的 `modelId`）、`title`、`status`、`biz`、`attrs[]`。

> ⚠️ 单个 Tab 的响应约 11 KB / 20 余字段。用 `--filter` 或结构化解析裁剪，不要把整份响应展开给用户。

### 3.3 取 modelId —— 禁止硬编码

`modelId` 一律取 `data[0].id`，**每次操作前现读**。

> 🔴 **`modelId` 是租户级的值，换一个租户就是另一组数字。** 而写接口 `/api/core/v1/field/*` 是部门与员工两侧共用的，**服务端不校验 `modelId` 属于哪个业务域** —— 传了员工档案的 `modelId`，字段就会静默建到员工档案里去，且两侧的 id 数值往往相邻、肉眼分不出。
>
> 因此：不得把任何样例里的数字写进请求，不得跨任务缓存复用，不得从对话上文里「记得」一个 `modelId` 就直接用。**每次都从本次 `model/list` 的响应里取。**

### 3.4 定位字段（attrId）

在 `data[0].attrs[]` 中按 `label` 匹配（trim + 大小写不敏感）：

| 命中数 | 处理 |
|---|---|
| 0 | 告知未找到；列出该 Tab 下全部字段（标注启用状态）供选择 |
| 1 | targetAttr = 该字段 |
| 多个 | 列出候选（label + id + type + isLimited）让用户确认 |

> `model/list` **同时返回启用与停用字段**，靠 `isLimited` 区分（附录 C）。

**跨 Tab 搜索**：用户只给字段名、Tab 无法判断时，两个 Tab 各查一次再合并候选；命中多个时必须让用户确认，不要按 Tab 顺序自行挑第一个。

### 3.5 写前预检（必做）

| 条件 | 处理 |
|---|---|
| `isLimited == 0` 且操作是停用 | **拒绝**，不发请求。提示「【xxx】是系统核心字段，不可停用」 |
| `isLimited == 0` 且操作是编辑 | **拒绝**，不发请求。这些字段同时是 `isCanModify == 0` |
| `isLimited == 2` 且操作是停用 | 提示「【xxx】已是停用状态」，不重复发请求 |
| `isLimited == 1` 且操作是启用 | 提示「【xxx】已是启用状态」，不重复发请求 |
| `isCanModify == 0` 且操作是编辑 | 提示该字段不允许修改，请用户确认后再试 |
| `isRequired == 1` 且操作是停用 | ⚠️ 未完全确认必填字段能否停用。先告知风险并要求用户确认，再发请求；若返回业务错误则按第 7 步处理 |

> 🔴 **判定只看 `isLimited`，不要看 `fieldName` 有没有 `DF_` 前缀。**
> `DF_` 前缀确实代表租户自建，但反过来不成立：`dept_type`（部门类型）、`dept_level`（部门层级）、`hrbp`（HRBP）都是系统预置的具名字段，却是 `isLimited == 1` / `isCanModify == 1`，可以停用也可以改。**按前缀拒绝会拦掉合法操作，按前缀放行会撞上核心字段。**

## 第 4 步：收集字段参数

### 4.1 通用参数

| 参数 | 说明 | 必填 |
|---|---|---|
| 字段名称 | → `label` | ✅ |
| 字段类型 | → `type`，见 §4.2 / §4.3 | ✅（创建时；组织职责固定值） |
| 所属 Tab | → `moduleId`，第 3.1 步结果 | ✅ |
| 提示文案 | → `tips`，对应列表页「提示」列 | 可选 |
| 是否必填 | → `isRequired`，0/1，默认 0 | 默认否 |
| 是否唯一 | → `isUnique`，0/1，默认 0；**仅部门信息(6) 有此键** | 默认否 |

用户未提及可选项时使用默认值，不要逐项追问。

### 4.2 部门信息(6) 支持的字段类型

| 用户描述 | type | 附加参数 |
|---|---|---|
| 单行文本 / 文本 | `1` | 无 |
| 多行文本 / 长文本 | `11` | 无 |
| 日期 / 时间 | `2` | 无 |
| 是否 / 布尔 / 是非题 | `4` | 无 |
| 单选 / 下拉 | `5` | `values` 选项数组，见 §4.4 |

**页面上只提供这 5 种，上表之外一律不创建。** 用户要求建数字、地址、电话、附件、部门选择器、人员等类型时，停下说明本页不支持，请在页面确认或改用其他设置页。存量数据里可能出现 `type 12`（上级部门，系统的部门选择器），那是系统预置的只读形态，见附录 A。

### 4.3 组织职责(7) —— 固定人员(17)

**组织职责的字段类型固定为 `17`（人员），页面上没有类型选择器。** 实测该 Tab 下全部字段无一例外都是 `type 17`。

创建时页面只有三项可填：**字段名称、提示、是否必填**。没有单选 / 多选之分，也没有可选范围配置。

用户在组织职责下要求建文本、日期等类型时，停下说明：组织职责的每个字段就是一个「职责槽位」，值只能是人员，请确认是否应该改建到部门信息(6) 下。

> ⚠️ **组织职责的 payload 键集合与部门信息不同**：不传 `isUnique`，也不传 `applyTargetLibrary`。见 §5.3 的键集合表。

### 4.4 单选(5) 的选项

**创建**时结构极简，`sortNo` 从 1 连续递增：

```json
"options": "",
"values": [
  {"value": "正式", "sortNo": 1},
  {"value": "外包", "sortNo": 2}
]
```

**编辑**时必须先读回原选项，规则见 §5.4.2。

## 第 5 步：接口调用

所有接口均为 **POST**，路径带 `?bus=20`，body 均含 `"loginType":"10"`。

> ⚠️ 本页用到两套前缀，**读写各一套**：
> - `/api/organization/v1/model/list` —— 查询（**部门专用**；员工档案用的是 `/api/organization/hr/setting/model/list`，两者不是同一个接口，不要互换）
> - `/api/core/v1/field/*` —— 详情、创建、编辑、停用、启用（**与员工档案共用同一批接口**，见 §3.3 的红线）
>
> **payload 里带不带 `bus` 由前缀决定，不由操作决定**：`/api/core/v1/*` 的 body 必须额外带 `"bus":"20"`；`/api/organization/*` 的不带。两侧的 query 都带 `?bus=20`。本页所有写请求都在 `core/v1` 下，因此 **body 一律带 `bus`**。

### §5.1 查询

见 §3.2。常见输出形态：

- 「部门信息有哪些字段」→ 列 `label` + 类型名 + 必填 + 启用状态
- 「有哪些组织职责」→ 列 `label` + 启用状态
- 「哪些字段被停用了」→ 过滤 `isLimited == 2`
- 导出报表 → 解析后生成文件，不要把原始 JSON 倒给用户

### §5.2 查询单个字段详情

```bash
cllmk curl \
  --url "/api/core/v1/field/detail?bus=20" \
  --method POST \
  --payload '{"attrId":<字段id>,"bus":"20","loginType":"10"}'
```

payload 只有 `attrId` —— 该 id 全局唯一，不需要 `moduleId` / `modelId` 作为上下文。

返回单个 attr 对象，与 `model/list` 的 `attrs[]` 近似同构，但**两侧各有对方没有的键**：

| 键 | `model/list` 的 attrs[] | `field/detail` |
|---|---|---|
| `values`（单选选项） | 恒为空 | ✅ 完整选项数组 |
| `isUnique` | ✅ 有 | ❌ **不返回** |
| `moduleId` | ❌ attr 层恒为 `null` | ❌ 恒为 `null` |

**这三行决定了编辑字段的读回策略，见 §5.4.1。**

### §5.3 创建字段

```bash
cllmk curl \
  --url "/api/core/v1/field/add?bus=20" \
  --method POST \
  --payload '<完整 JSON>'
```

**部门信息(6)** 的 payload：

```json
{
  "label": "<字段名称>",
  "tips": "<提示文案>",
  "type": <1|11|2|4|5>,
  "moduleId": 6,
  "modelId": <本次 model/list 读到的 id>,
  "attrId": null,
  "isRequired": 0,
  "isUnique": 0,
  "options": "",
  "isGroupTitle": 0,
  "applyTargetLibrary": true,
  "bus": "20",
  "loginType": "10"
}
```

**组织职责(7)** 的 payload：

```json
{
  "label": "<职责名称>",
  "tips": "<提示文案>",
  "type": 17,
  "moduleId": 7,
  "modelId": <本次 model/list 读到的 id>,
  "attrId": null,
  "isRequired": 0,
  "options": "",
  "isGroupTitle": 0,
  "bus": "20",
  "loginType": "10"
}
```

**两个 Tab 的键集合不同，必须分支构造：**

| 键 | 部门信息(6) | 组织职责(7) |
|---|:-:|:-:|
| `label` `type` `moduleId` `modelId` `attrId` `isRequired` `options` `isGroupTitle` `bus` `loginType` | ✅ | ✅ |
| `tips` | 可省略 | 可省略 |
| `isUnique` | ✅ | ❌ **不传** |
| `applyTargetLibrary` | ✅ 固定 `true` | ❌ **不传** |
| `values` | 仅单选(5) | — |

其他约定：

- 不传 `sortNo`，新字段追加到末尾。
- `options` 一律传 `""`。
- `applyTargetLibrary` 在部门信息下固定传 `true`，无需询问用户：该参数服务于其他场景，在本页被隐藏且无实际作用。
- 创建后可回读 `model/list` 验证；新字段的 `fieldName` 会是 `DF_` 前缀的随机串。

### §5.4 编辑字段

```bash
cllmk curl \
  --url "/api/core/v1/field/edit?bus=20" \
  --method POST \
  --payload '<完整 JSON>'
```

#### 5.4.1 edit 是全量覆盖，且读回要读两处

`field/edit` 的 payload 与 `field/add` 同构，只是 `attrId` 填真实 id。**漏传的键会被重置**，所以编辑前必须把原值读齐。

> 🔴 **单独一个接口读不齐。** 按 §5.2 的表：`values` 只有 `field/detail` 有，`isUnique` 只有 `model/list` 有，`moduleId` 两个都没有。

固定的读回顺序：

1. **`model/list`**（§3.2）→ 拿 `label` / `tips` / `type` / `isRequired` / `isUnique` / `isGroupTitle` / `options`，以及 `modelId`。
2. **仅当 `type == 5`** → 再调 `field/detail`（§5.2）拿 `values`。
3. **`moduleId` 由第 3.1 步的 Tab 判断带入**（`6` 或 `7`），**不要试图从任何响应里读** —— 两个接口的 attr 层都返回 `null`。

⚠️ `moduleId` 传错会把字段挪到另一个 Tab。用户只说改名时，`moduleId` 与 `modelId` 都必须原样传回，不能省略也不能改动。

#### 5.4.2 编辑单选字段的 `values`

`field/detail` 返回的 `values[]` 每项带 `id`（选项 id）、`value`、`sortNo` 及一批只读标志位。回写时：

- **保留的选项**：原样带上 `id`，不要重新编号。
- **新增的选项**：不传 `id`，`sortNo` 接在现有最大值之后。
- **删除的选项**：从数组里去掉即可。删除会影响已填该值的部门数据，**必须在确认环节单独列出**。

不确定某个只读标志位的含义时，把 `field/detail` 返回的该项原样回传，不要自行构造或省略。

### §5.5 停用 / 启用字段

```bash
cllmk curl \
  --url "/api/core/v1/field/disable?bus=20" \
  --method POST \
  --payload '{"attrId":<字段id>,"modelId":<本次读到的 id>,"bus":"20","loginType":"10"}'
```

启用把 `disable` 换成 `enable`，payload 完全相同。

- 两个 Tab 用同一组接口，payload 里**不带 `moduleId`**。
- 停用后 `isLimited` 变 2，字段在部门档案中不再显示，**已填数据保留**。启用后回到 1。
- 系统核心字段（`isLimited == 0`）不允许停用，按 §3.5 的预检在客户端拦掉，不发请求。

### §5.6 不要调用的噪声接口

页面操作时会伴随下列请求，**skill 一律不调用**：

| 接口 | 性质 |
|---|---|
| `/api/common/v1/formLinkageRule/ruleList`、`.../getTotalCount` | 联动规则 |
| `/api/universal/pushmsg/getUnreadMsgCount` | 消息红点 |
| `/api/gateway/gray`、`/manifest.json` | 基础设施 |
| `*.fc.aliyuncs.com/.../write_log/` | 前端埋点。**body 里带登录人姓名、邮箱与公司名，既不要调用，也不要把抓到的这类请求贴进文档**（AGENT.md §5 红线 6） |

写操作后页面会自动重新拉 `model/list`；skill 可按需自行回读验证，但那是独立决策，不是接口的必需步骤。

## 第 6 步：调用前确认

任何写操作（创建 / 编辑 / 停用 / 启用）前，必须展示完整请求并获得确认：

```
即将执行以下操作（创建 / 编辑 / 停用 / 启用）：

接口：POST {接口路径}
当前会话：people / {env} / {corpName}（tenantId {tenantId} / buId {buId}）
位置：部门信息设置 → {Tab 名}（moduleId {moduleId} / modelId {modelId}）
字段：{字段名}（类型：{类型名}{，已有字段 id}）

请求内容：
{格式化 JSON payload}

影响范围：部门字段为全租户共享配置，改动对所有部门生效。

确认执行？
```

**分类型追加：**

- **创建**：复述目标 Tab 名，并说明 `modelId` 是本次实时读到的值。
- **编辑**：展示「变更前 → 变更后」逐项对照，明确列出**未变更但仍会提交的键**，说明这是全量覆盖接口。
- **编辑单选**：展示选项对照表，标注哪些保留 `id`、哪些是新增、哪些被删除。
- **停用**：说明停用后字段在部门档案中不再显示，已填数据保留。
- **批量操作**：先展示完整清单和总数，逐条执行并汇报进度；任一条失败即停止并报告已完成/未完成。

用户回复「确认」「可以」「执行」「ok」「是」等明确指令后才继续，其他回复视为未确认。

## 第 7 步：处理响应

| 响应 | 处理 |
|---|---|
| 内层 `code == 200` | 成功。展示关键结果（新字段 ID、变更摘要）。写操作后可选回读 `model/list` 验证 |
| 内层 `code != 200` | **业务失败**。展示 `msg`，检查参数（字段名重复、类型非法、必填缺失等）。不要因为外层 `code == 0` 就报告成功 |
| HTTP 401 / 403 | 跑裸 `cllmk auth status` 验证；明确失效才引导重新登录，否则报告权限问题 |
| HTTP 4xx 其他 | 展示错误详情，提示检查参数 |
| HTTP 5xx | 服务端错误，建议稍后重试 |
| `Request failed`（网络） | 按 `<skill-dir>/references/foundation/auth.md` 的「受限执行环境的网络重试」处理。**写请求不可盲目重试** —— 先用 `model/list` 回读确认是否已生效 |

## 不覆盖清单

以下能力**不在本 skill 覆盖范围**，用户提出时停下说明并建议在页面手工操作：

## 附录 C：状态位速查

People 全系统统一约定：**0 = 系统锁定 / 1 = 启用 / 2 = 停用**。

| 对象 | 键 | 0 | 1 | 2 |
|---|---|---|---|---|
| 字段 | `isLimited` | 系统核心字段，不可停用 | 启用中 | 已停用 |
| 分组 | `status` | 系统内置分组，常驻 | 启用中 | 已停用 |

本页两个 Tab 的分组恒为 `status == 0`。

**不要用这些键判断状态**（实测在本模块内无区分度）：`isShow`、`sensitivity`、`isCanApprove`。

其他常用键：

| 键 | 说明 |
|---|---|
| `fieldName` | `DF_` 前缀 = 租户自建字段；其余为系统预置。**但系统预置不代表不可改，判定看 `isLimited`**（§3.5） |
| `isRequired` | 0/1，对应列表页字段名后的 `*` |
| `isCanModify` | 0/1，是否允许修改 |
| `isCanModifyRequired` | 0/1，是否允许改必填 |
| `biz` | 分组业务标识：部门信息为 `dept_prop`，组织职责为 `dept_duty` |
| `title` | 分组名。⚠️ 组织职责 Tab 的服务端 `title` 是「**部门职责**」，与页面和用户口中的「组织职责」不一致，按 `moduleId` 定位，不要按 `title` 匹配 |
