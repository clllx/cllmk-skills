# cllmk curl：调用规范与背景说明

本文是**写 skill 时的规范参考**，不随技能分发，模型运行时读不到它。

因此这里只承担两件事：一是给写业务文档的人一份 `cllmk curl` 的完整说明，让 `operations/` 里的每条 curl 命令都按同一套规范写出；二是记录这套规范背后的原因。
凡是模型**执行时**必须知道的约束，都已经落在它读得到的地方 —— 见 §5，不允许只写在本文。

## 1. 命令签名

```bash
cllmk curl --url <url> [--method <method>] [--payload <json>] [--filter <path>]
```

- `--url` 必填，相对路径自动拼当前会话的 baseUrl，也接受完整 URL；`--method` 默认 `GET`；`--payload` 是作为请求 body 的 JSON 字符串。
- CLI 自动注入 current 会话的 Cookie 和 `Content-Type: application/json`。**业务文档里不要出现手拼 Cookie 的写法** —— 那既绕开了 current，又会把凭证写进命令行和 shell 历史。
- `--filter` 只在输出中保留指定响应路径，是本地筛选。

业务 curl 始终使用 current：命令不得携带 `--org` / `--profile`，也不允许靠 `CLLMK_PROFILE` 路由。发请求前的会话检查、401/403 复验属于鉴权，规则在 `foundation/auth.md`。

两侧示例形态（写文档时照各自系统的来）：

```bash
# ATS：GET + filter
cllmk curl --url "/api/v2/org/info" --method GET --filter jobFields

# People：POST + payload（业务键的取值一律由业务文档给出，不在规范里编造）
cllmk curl --url "/api/organization/hr/setting/model/list?bus=20" \
  --method POST --payload '{"loginType":"10","moduleId":<moduleId>}'
```

## 2. `--filter` 路径语法与版本差异

`--filter` 是**本地**筛选，只裁剪输出，不改变服务端返回的内容。因此它的失败和接口的失败是两件事 —— 混淆这一点会直接得出错误的业务结论。

| CLI 版本 | 语法 | 路径不存在时 |
|---|---|---|
| `>= 0.2.0` | 点号分隔对象键，纯数字段表示数组下标，如 `data.list.0.name` | 返回 `code: 1` 和明确的 filter 错误 |
| `0.1.1` | 只能穿过普通对象，**不能进入数组**，不支持下标 | **静默返回 `null`** |

三条判读规则：

- **用 `code` 区分「路径错误」和「真实空值」**（`>= 0.2.0`）：对象键不存在、数组段不是数字、下标越界都返回 `code: 1`；字段真实存在且值就是 JSON `null` 时返回 `code: 0`。
- **filter 失败不是接口业务结论**：`code: 1` 且消息指向 filter 路径时，只能说明本地筛选没成功。先改读不含敏感数据的最小父路径，必要时把响应存到权限受控的临时文件后只检查顶层键；只有确认原始业务响应确实缺少该字段，才能报告「当前租户未返回此配置」。不得把 filter 错误表述成租户无配置或接口失败。
- **非 0 下标前面的 `null` 是占位，不是空值**：为保留原下标，`data.list.1.name` 会序列化成类似 `{"data":{"list":[null,{"name":"李四"}]}}`。必须读请求的原下标，不得改读 `list[0]`，也不得把占位判成字段空值。

`0.1.1` 遇到数组场景的 fallback：先过滤到完整数组（如 `data.list`），再用 `jq`、Python 或业务脚本解析实际输出结构。旧版缺失路径静默返回 `null`，**不得据此判断接口没有返回该字段**。任务确实需要数组下标而版本低于 `0.2.0` 时优先用这个 fallback；只有用户要求升级才按 `install.md` 安装最新版，不要在旧版上试跑新语法。

这三条里最危险的是第二条与 `0.1.1` 的组合：静默 `null` 和「字段真的没有」在输出上完全一样。**凡是业务文档要读数组下标，就必须在该文档里写明这个分支**（§5）。

## 3. 失败分支

与 status 不同，**curl 遇到非 2xx 响应不会自动清除会话**：

| curl 输出 | 含义 | 应对 |
|-----------|------|-----------|
| `code: 0` | HTTP 请求成功 | `data` 含响应体。**外层 `code: 0` 只代表 HTTP 通了**，业务成败按各系统的业务码判定（ATS 看外层 `code == 0` 即可，People 必须看响应体内层 `code == 200`） |
| `code: 1, msg: "HTTP 401"` | 可能凭证失效 | 跑裸 `cllmk auth status` 验证 current；明确失效才按 `auth.md` 重新登录 |
| `code: 1, msg: "HTTP 403"` | 业务权限不足或接口拒绝 | 跑裸 `cllmk auth status`；会话有效则报告权限问题，会话检查仍为 403 时保留凭证并停止 |
| `code: 1, msg: "HTTP 404"` | 接口路径不存在 | 确认 URL；不同 system 接口不同 |
| `code: 1, msg: "HTTP 4xx"` 其他 | 业务错误 | 报告给用户，由业务流程决定重试或终止 |
| `code: 1, msg: "HTTP 5xx"` | 服务器错误 | 提示稍后重试 |
| `code: 1, msg: "Not logged in ..."` | 该 profile 未登录 | 按 `auth.md` Step 5 的 `Not logged in` 分支处理 |
| `code: 1, msg: "--url is required"` / `"--payload must be valid JSON"` | 参数错误 | 修正后重试 |
| `code: 1, msg: "Request failed: ..."` | 网络或执行环境限制 | 按 `auth.md`「受限执行环境的网络重试」根据方法幂等性处理；**写请求不得盲目重试** |

401 / 403 这两行是**鉴权分支**，模型运行时必须知道，所以它们同时写在 `foundation/auth.md` 的「curl 与鉴权的衔接」里 —— 那不是重复，那是它们的正式落点，本文这份是规范全表的一部分。

## 4. 响应展示约束

`curl` 响应不因「不含凭证明文」就可以完整展示。优先使用 `--filter`、结构化解析或业务脚本，只向用户返回完成任务所需字段。

- ATS 侧：候选人简历、邮箱、电话、证件信息和附件地址等敏感业务数据不得无关展开。
- People 侧：员工证件号、银行卡号、联系方式等个人敏感信息不得无关展开。
- 响应体积大的接口（如 ATS 的 `/api/v2/org/info`、People 的字段分组列表）必须先 `--filter` 或按脚本解析，不要把整份响应读进上下文或打到终端。

这一条是 AGENT.md §5 红线 2 的延伸，**对所有业务路由都成立**，因此它的执行落点是两个 `SKILL.md` 的「全局安全规则」，不是某一份 foundation 文档。

## 5. 写业务文档时怎么落地本规范

模型运行时**不会**读到一份通用 curl 手册。它读的是「业务公共前置 + 一个 operations 主文档」。所以规范靠三个落点生效：

| 规范内容 | 执行落点 | 写法 |
|---|---|---|
| 命令怎么写（§1） | 各 `operations/` 主文档 | 直接写出完整可执行的 `cllmk curl ...`，不写「按 curl 规范自行拼装」 |
| `--filter` 数组陷阱（§2） | **用到数组下标的那份**业务文档 | 在该 filter 命令旁边内联 2–3 行：`0.1.1` 静默返回 `null`、改读最小父路径、不得判成租户无配置 |
| 401 / 403 复验（§3） | `foundation/auth.md`「curl 与鉴权的衔接」 | 已在那里，不要再抄一份到业务文档 |
| 响应展示约束（§4） | 两个 `SKILL.md`「全局安全规则」 | 已在那里，对所有路由生效 |

写新业务文档时的自检：**这条 curl 命令如果只有它自己被读到，模型能不能正确执行并正确判读失败？** 不能，就说明缺的那部分要内联进去，而不是指望模型去读别的文件。

## 6. 为什么 curl 规则不放在 skill 内

曾经有过一份 `foundation/curl.md`（由 `auth.md` 拆出，因为业务文档要找的是 `--filter` 规则却只能指向一个名字叫「鉴权」的文件）。它随后被移到本文，原因是加载纪律：

业务任务只读「业务公共前置 + 一个 operations 主文档」。一份通用 curl 手册要么根本不会被读到，要么需要在每份业务文档里加一次跳转 —— 而真正需要的只是那两三行数组陷阱判定。**把手册塞进 skill 是用四份文件的维护成本换一个不会发生的读取**。

skill 内保持纯净的代价是本文必须被人主动读到：新增涉及 curl 的业务文档时，按 §5 的三个落点检查一遍。这是 AGENT.md §7 的一部分。

## 7. 两侧差异

规范本身两侧一致（命令签名、`--filter` 版本规则、失败分支形态）。差异只有两处，写业务文档时按所属系统取：

| | ats | people |
|---|---|---|
| 示例接口 | `/api/v2/org/info --filter jobFields` | `model/list`（POST + payload） |
| 业务成功码 | 外层 `code == 0` 即成功 | 外层 `code: 0` 只代表 HTTP 通了，业务成败看响应体内层 `code == 200` |

People 侧曾经出现过直接抄 ATS 接口路径的历史，见 `doc/auth.md` §10 —— 示例里的接口路径不是可跨系统套用的模板。
