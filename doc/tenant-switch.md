# cllmk 租户切换：背景说明

本文是 `skills/ats/references/foundation/tenant-switch.md` 的人类阅读版补充：记录「为什么这么设计」。
`skills/` 只写模型执行时需要的步骤与硬约束；本文不随技能分发，模型不会读到，**因此任何执行必需的规则都不允许只写在这里**。

## 1. 为什么列表命令是「无参数 switch」而不是 `auth list`

`cllmk auth switch` 不带参数时列出所有已保存会话并标记 current，带参数时才切换。没有单独的 `auth list` 子命令 —— 执行它得到的是 `error: unknown command 'list'`。

skill 里专门写明这一点，是因为这条错误信息很容易被误读成「CLI 版本太旧」，进而触发一次没必要的升级安装，甚至在升级失败后放弃整个任务。它其实只是命令名不存在。

## 2. 为什么列表是离线的

列表直接读本地凭证文件的身份快照，不发网络请求。好处是快、且在断网时仍能告诉用户「盘上有哪几家公司的会话」；代价是它**不能证明会话还活着** —— Cookie 可能已经过期。

所以查询和验证被拆成两步：离线列表负责「有哪些、指针在哪」，实时 `auth status` 负责「现在这份还能用吗」。用户问「我现在登录的是哪家」时只看列表就回答，会在凭证过期的情况下给出错误结论。

## 3. 为什么租户 ID 和公司名合并判重

`--org` 既接受租户 ID 也接受公司名。实现上没有「先按 ID 匹配，匹配不到再按公司名」的优先级 —— 两者一起匹配，命中多个就返回 `matches multiple profiles` 并保持 current 不变。

这是刻意放弃了「智能猜测」：ID 和公司名同时命中不同 profile 时，任何隐式优先级都可能让用户在 A 公司的意图落到 B 公司上，而写操作一旦落错租户无法回滚。停下来问一句的成本远低于此。

位置参数是唯一有优先级的地方（profile 名优先于租户身份），因此已知目标类型时应该用显式参数，不要依赖它。

## 4. 为什么切换后 status 失败也不自动回滚

切换成功后 current 已经写盘。此时实时验证失败（过期、未登录、身份不符），直觉动作是用响应里的 `previous` 切回去 —— skill 明确禁止这么做。

原因是 current 是同一配置目录的**共享状态**：用户可能已经在另一个终端里做了别的选择，自动回滚会二次改动共享状态并覆盖它。正确动作是保留新 current、如实报告「指针已切到 X，但实时验证失败」，把决定权交回用户。

同理，跨租户任务收尾必须明示指针最终停在哪家 —— 用户的下一条裸命令会落在那里。默默留下一个与任务开始时不同的指针，是这套设计里最容易造成事故的形态。

## 5. 为什么把 `CLLMK_PROFILE` 检查放在切换之前

环境变量的优先级高于 current 指针。如果它非空而没有被发现，会出现这种错位：`switch` 确实更新了持久化 current，但随后的裸 `auth status` 和业务命令仍被环境变量路由到另一个 profile —— 验证通过的是 A，实际操作的是 B。

因此 skill 要求切换和进入业务前必须先要求用户清除它，只有「纯粹读无参数列表」这一种情况允许带着它继续（列表读的是持久化指针，不受影响），且必须同时提示覆盖风险。

## 6. 修改 tenant-switch.md 时

- 它是 current 租户规则的单一事实来源，`ats` 与 `people` 共用一份；改动必须评估两侧影响，并按 AGENT.md §9 在 commit message 里显式说明影响面。
- 登录、登出、过期与 API 鉴权分支属于 `auth.md`，不要在本文件里重复一份 —— 两处描述同一个分支，改动时必然漏掉一处。
- 安全红线（AGENT.md §5）在本文件里必须保持禁止语气。「不自动回滚」「不猜测」「不并行」都是硬约束，不是可选建议。
